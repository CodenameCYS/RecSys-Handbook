# 长期策略

长期策略将当前列表选择与探索、疲劳、留存及未来价值联系起来。它们不在最终列表生成后“再执行一次”，而是在一次请求开始时，利用跨请求的模型、预算和状态选择策略版本、探索动作或目标权重，再交由[列表重排](../列表重排/README.md)或[约束优化与编排](../约束优化与编排/README.md)在可行候选中完成选择。

任何长期策略都建立在稳定的曝光日志、策略版本、反事实评估与安全护栏之上，且不能绕过[基础规则与约束](../基础规则与约束/README.md)。短期点击提升不等于长期收益；没有明确奖励、归因窗和对照策略的离线结果也不能证明因果收益。

## 1. 请求与反馈契约

| 输入/状态 | 用途 | 必须记录或版本化的语义 |
| --- | --- | --- |
| 合格候选与基础效用 | 限定可选动作空间 | 必须是硬规则后的候选集及其快照 |
| 请求上下文 | 输入 Bandit 或策略模型 | 特征版本、缺失值和隐私处理口径 |
| 用户疲劳、探索预算 | 约束探索幅度 | 窗口、刷新频率和读失败语义 |
| 策略/模型状态 | 产生动作、权重或 slate | `policy_id`、模型版本、随机种子或随机化版本 |
| 反馈事件 | 构造短期与长期奖励 | 曝光定义、归因窗、迟到/撤回和幂等键 |

每个决策日志至少包含 `request_id`、候选集摘要、动作/最终列表、位置、`policy_id`、`model_version`、`policy_mode`、被选动作的倾向分数（propensity）、探索预算、输入状态快照版本和降级原因。曝光、点击、消费、负反馈与留存标签应能用相同的请求和展示 ID 关联；仅记录点击样本会产生选择偏差。

## 2. 运行时闭环

```mermaid
flowchart LR
	A[L2 候选与请求上下文] --> B[基础规则与约束]
	B --> C[策略选择
版本、探索预算、权重]
	C --> D[重排或联合编排]
	D --> E[最终列表与倾向日志]
	E --> F[客户端曝光与反馈]
	F --> G[归因、奖励聚合与延迟处理]
	G --> H[离线评估、训练与发布审查]
	H -. 批准的模型/策略版本 .-> C
```

策略层只能在 $\mathcal{C}_{eligible}$（硬规则后的候选）内选择；策略无法满足 deadline、状态不可用或探索预算耗尽时，必须返回已批准的相关性基线或缓存策略，不得扩大可选集合。

## 3. 复杂度、状态访问与 deadline

令 $N$ 是可行候选数，$K$ 是最终位置数，$F$ 是在线特征数。逐候选上下文打分通常为 $O(NF)$，选择前 $K$ 个为 $O(N\log K)$ 或使用选择算法近似为 $O(N+K\log K)$；Slate 联合动作的精确空间随 $N$、$K$ 组合增长，不能在请求路径枚举。

请求路径应批量读取策略状态和预算，禁止为每个候选读取一次用户或 Bandit 状态。区分特征读取、模型打分、策略随机化、重排/求解及日志投递的耗时；反馈聚合、模型训练和策略发布应异步进行。状态过期、模型超时、日志投递失败均应有可观测的 `policy_mode`，其中日志失败不应静默继续探索。

## 4. 评测、发布与治理

- 离线评估必须检查日志覆盖、propensity 合法性、支持集重叠、奖励迟到与策略版本漂移；不满足支持集条件时，IPS/SNIPS/DR 等反事实估计不可信。
- 线上采用小流量、可暂停实验，联合观察用户效用、消费质量、负反馈、疲劳、留存代理、探索率、策略延迟与回退率。
- 延迟长期标签应先冻结归因窗，再比较同口径的策略；训练、评估和线上奖励口径不一致会制造伪提升。
- 策略版本、奖励权重、探索预算和发布审批必须可审计。涉及敏感人群或高风险业务时，需额外经过隐私、合规和风险审查。
