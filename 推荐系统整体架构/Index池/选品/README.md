# 选品

选品模块从全量商品池中持续计算可推荐商品集合。它处于商品主数据与检索索引之间，重点是资格治理而非个性化排序。

## 一、输入与输出

### 输入

- 商品主数据：商品 ID、类目、商家、创建时间和内容字段。
- 生命周期状态：上架、下架、有效期、库存、可售状态和删除状态。
- 风险与审核结果：内容安全、版权、黑名单、投诉和人工审核。
- 场景约束：地域、语言、渠道、终端、业务线和用户权限。
- 质量信号：完整度、清晰度、重复度、刷量风险、商家信誉和历史反馈。
- 运营策略：白名单、黑名单、新品池、活动池和实验配置。

### 输出

选品结果应包含资格、适用范围和原因，而不是只输出商品 ID：

```json
{
  "item_id": 10001,
  "eligible": true,
  "scopes": ["home_feed", "shanghai"],
  "reason_codes": [],
  "valid_from": "2026-08-20T00:00:00Z",
  "valid_to": "2026-09-20T00:00:00Z",
  "metadata_version": 17,
  "updated_at": "2026-08-20T08:30:00Z"
}
```

## 二、规则分层

### 1. 基础有效性

- 商品处于允许推荐的上架状态。
- 当前时间落在 `valid_from` 与 `valid_to` 之间。
- 库存、供给容量或服务状态满足最低要求。
- 必填字段、媒体资源和落地页完整可用。
- 商品未被删除，关联商家或作者仍然有效。

这类规则通常是硬过滤，应尽量由权威状态源驱动，而不是从行为日志推测。

### 2. 安全与合规

- 违法、暴力、色情、欺诈及其他有害内容检测。
- 版权、品牌、资质、广告法和行业监管检查。
- 用户举报、黑名单和人工审核结论。
- 未成年人、敏感类目、地域与人群限制。

机器模型可以提供风险分，但最终准入逻辑需要可解释的策略阈值和原因码。高风险状态更新应优先进入实时链路。

### 3. 场景资格

商品可能在一个场景有效、另一个场景无效。例如本地生活商品受地域约束，订阅内容受会员权限约束，某些媒体格式只适用于特定终端。

推荐使用 `eligible_scopes` 或资格位图表达多场景资格，避免为每个场景复制整份商品数据。

### 4. 质量与策略

- 低质量、重复或疑似刷量商品可以过滤或降权。
- 新品可以进入专用探索池，而不是直接与成熟商品使用同一阈值。
- 运营白名单只能覆盖允许覆盖的质量规则，不能绕过安全合规硬规则。
- 供给公平、商家限额等列表级问题通常留给 L3，Index 层只维护必要资格和基础分层。

## 三、处理链路

```mermaid
flowchart LR
    A[商品快照与变更事件] --> B[字段校验]
    B --> C[生命周期校验]
    C --> D[安全合规]
    D --> E[场景资格]
    E --> F[质量与策略]
    F --> G[可推荐状态表]
    G --> H[Index 增量更新]
```

### 离线全量链路

用于初始化、规则变更后的重算、审计和数据修复。全量任务应保证输入快照一致，并输出规则版本与统计报告。

### 实时增量链路

监听上下架、库存、审核和有效期事件，更新单个商品的资格状态。需要处理乱序、重复、迟到事件，通常以商品版本号或事件时间实现幂等更新。

### 定时过期扫描

仅依赖事件可能漏掉到期商品。应使用时间轮、延迟队列或定时扫描，在 `valid_to` 到达时主动撤销资格。

## 四、规则优先级与状态机

推荐采用“硬规则优先、显式覆盖、默认拒绝敏感场景”的原则。一个简化状态机如下：

```text
DRAFT -> PENDING_REVIEW -> ELIGIBLE -> EXPIRED
                         -> BLOCKED
ELIGIBLE -> SUSPENDED -> ELIGIBLE
ELIGIBLE -> SOLD_OUT / OFFLINE / BLOCKED
```

状态转换必须记录触发源、前后状态、规则版本和时间。恢复操作也应经过权威事件，而不是简单删除黑名单记录。

## 五、去重与商品族

重复商品可能来自重复发布、不同 SKU、镜像内容或近重复媒体。需要区分：

- **精确重复**：相同业务主键、内容哈希或资源哈希。
- **近似重复**：文本、图像或向量高度相似。
- **商品族**：同一 SPU 下的不同 SKU，是否合并取决于推荐场景。

Index 层应产生 `canonical_item_id`、`family_id` 或重复簇，供召回去重和 L3 打散使用；不应在缺乏业务语义时直接删除所有相似商品。

## 六、失败处理与回溯

- 单条异常进入死信队列，不阻塞整个批次。
- 规则服务不可用时，安全规则默认保守，质量规则可按已发布版本降级。
- 每个商品保留最近若干状态版本，支持审计和回滚。
- 重算结果先与在线版本做差异分析，再发布大规模状态变化。
- 对大批量误杀设置变化率告警和发布熔断。

## 七、监控与评测

| 指标 | 目的 |
| --- | --- |
| 可推荐商品数及分场景分布 | 发现供给异常收缩或膨胀 |
| 各规则过滤数量与占比 | 发现规则漂移或上游状态异常 |
| 误杀率与漏放率 | 衡量选品准确性 |
| 状态更新 P95/P99 延迟 | 衡量上下架和风控生效速度 |
| 到期未下线数量 | 验证有效期机制 |
| 规则版本覆盖率 | 检查发布一致性 |
| 增量积压与死信数量 | 监控实时链路健康度 |

误杀和漏放需要通过抽样审核、用户投诉、风控回流与业务申诉联合估计。仅观察最终曝光量无法区分选品问题和召回问题。

## 八、与下游的接口

选品模块向 Index 构建模块输出：

- 可推荐商品 ID 与场景资格。
- 商品状态版本、有效期和更新时间。
- 必要的过滤字段与原因码。
- `ADD`、`UPDATE`、`DELETE` 类型的增量变更。

Index 构建模块应幂等消费这些变更，并在查询结果返回前再次检查高动态、高风险状态。这样既保证索引效率，也缩短紧急下线的生效时间。
