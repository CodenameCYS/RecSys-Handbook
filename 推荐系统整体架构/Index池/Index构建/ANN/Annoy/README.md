# Annoy：随机投影树森林

Annoy（Approximate Nearest Neighbors Oh Yeah）使用多棵随机投影树反复划分向量空间。单棵树把查询快速引导到一个较小叶节点，多棵树再从不同随机视角提供候选，降低一次错误划分造成的漏召回。

它的工程特点与算法结构紧密相关：树在离线构建完成后基本只读，因此索引很适合保存为文件、通过 mmap 加载，并由同一台机器上的多个进程共享物理内存页。

## 单棵树如何划分空间

构建一个内部节点时，可以从当前节点包含的向量中随机选取两个点 $\boldsymbol p$ 和 $\boldsymbol q$。以两点连线方向作为法向量，并在两点中间放置一个超平面：

$$
\boldsymbol n = \boldsymbol p - \boldsymbol q
$$

$$
b = -\boldsymbol n^{\mathsf T}\frac{\boldsymbol p + \boldsymbol q}{2}
$$

对任意向量 $\boldsymbol x$，根据

$$
\boldsymbol n^{\mathsf T}\boldsymbol x + b
$$

的正负把它分到左右子树。这个超平面近似垂直平分 $\boldsymbol p$ 和 $\boldsymbol q$，从而把当前空间沿随机方向切开。

递归划分直到节点中的商品数量足够少，该节点成为叶节点并直接保存一组内部 ID。树的每一层都缩小候选区域，所以查询只需从根走到少量叶节点，而不是遍历全部商品。

Annoy 的具体实现会包含平衡划分、重新采样和紧凑节点布局等细节，但理解其核心只需抓住“随机选择方向并递归二分空间”。

## 为什么需要多棵树

树的上层切分影响很大。如果两个真正相近的向量恰好被某个超平面分到两侧，只沿一条分支搜索就会漏掉近邻。

Annoy 构建多棵使用不同随机切分的树：

1. 同一对向量可能在第一棵树中被提前分开。
2. 它们在另一棵树中可能直到很深的层级仍位于同一区域。
3. 查询合并所有树产生的候选后，再用真实距离排序。

因此，`n_trees` 越大，相当于用更多随机空间划分观察数据，召回通常提高；代价是构建更慢、索引文件更大。

## 构建过程

1. 使用连续内部 ID 添加全部向量。
2. 重复构建 `n_trees` 棵随机投影树。
3. 每棵树递归生成内部划分节点和叶节点。
4. 把森林及叶节点中的 ID 组织成适合顺序读取的紧凑结构。
5. 保存索引文件，并单独持久化“内部 ID 到业务商品 ID”的映射。

Annoy 要求加入索引的 ID 为非负整数，并会按最大 ID 分配相关结构。若直接使用很稀疏的超大业务 ID，可能浪费大量空间，因此示例使用从 0 连续递增的内部 ID，再映射回业务 ID。

## 查询过程

最简单的树查询会在每个内部节点判断查询位于超平面的哪一侧，并沿对应分支下降到叶节点。但只走唯一分支召回不足，Annoy 实际会执行优先队列搜索：

1. 将每棵树的根节点加入候选队列。
2. 根据查询到划分边界的关系，优先访问更可能包含近邻的分支。
3. 同时保留另一侧分支作为后备路径，因为查询靠近边界时两侧都可能有近邻。
4. 持续展开树节点，直到检查节点数达到 `search_k` 预算。
5. 合并到达叶节点后获得的内部 ID，并去重。
6. 对候选计算真实距离，返回 Top-K。

所以 `search_k` 不是“返回候选数”，而是查询愿意检查的树节点预算。预算越大，搜索会探索更多备选分支，召回通常越高，延迟也随之增加。未显式指定时，Annoy 通常根据 `n_trees × top_k` 形成默认预算。

## Angular 距离

示例使用 `metric="angular"`。对归一化向量，Annoy 的 angular 距离与余弦相似度单调等价，可写成：

$$
d_{\text{angular}}(\boldsymbol x, \boldsymbol y)
= \sqrt{2 - 2\cos(\boldsymbol x, \boldsymbol y)}
$$

因此余弦越大，angular 距离越小，两者的近邻排序一致。API 返回的是距离，不是相似度分数，业务层不要直接把数值越大解释为越相关。

## 参数为何影响效果

| 参数 | 作用阶段 | 增大后的效果 | 主要代价 |
| --- | --- | --- | --- |
| `n_trees` | 构建 | 空间划分视角更多，召回通常提高 | 构建时间和索引体积增加 |
| `search_k` | 查询 | 展开更多节点和备选分支，召回通常提高 | 查询延迟增加 |
| `top_k` / `n` | 查询 | 返回结果更多，默认搜索预算也可能增加 | 排序与候选需求增加 |

`n_trees` 决定索引本身，修改后必须重建；`search_k` 可在每次查询时单独设置。同一索引可以为不同延迟等级使用不同 `search_k`。

## 与示例代码的对应关系

[index.py](./index.py) 中：

- `AnnoyIndex(dimension, metric="angular")`：创建指定维度和距离的索引。
- `add_item(internal_id, vector.tolist())`：以连续内部 ID 添加向量。
- `build(n_trees=20, n_jobs=-1)`：并行构建随机投影树森林。
- `save` / `load`：保存索引文件并通过只读方式重新加载。
- `get_nns_by_vector(..., search_k=2_000)`：按节点预算搜索森林。
- `item_ids[internal_id]`：将 Annoy 内部 ID 还原为业务 ID。
- `unload()`：显式解除 mmap，避免 Windows 上临时文件仍被占用。

运行示例前安装依赖：

```powershell
pip install annoy
python .\index.py
```

## 适用场景与限制

Annoy 适合以下模式：离线批量构建索引，发布不可变版本，在线服务只读加载；一台机器启动多个 worker 时，mmap 能减少重复常驻内存。

它不适合高频在线增删。调用 `build` 后不能继续按普通流程修改森林，通常需要在后台构建新版本，再原子切换索引文件。生产系统还应把业务 ID 映射、向量模型版本、距离度量和构建参数与索引文件一起版本化。

与 HNSW 相比，Annoy 的树文件易于只读分发和共享，但在高召回、低延迟场景中往往需要较多树或较大的 `search_k`。两者没有脱离数据分布和硬件的固定胜负，必须在相同 Recall@K 下比较 P99 与内存。
