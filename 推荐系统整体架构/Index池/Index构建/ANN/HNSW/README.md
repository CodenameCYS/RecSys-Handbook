# HNSW：分层可导航小世界图

分层可导航小世界图（Hierarchical Navigable Small World, HNSW）把每个向量看作图节点，并让相近节点互相连边。查询不再扫描全部向量，而是从一个入口节点出发，沿着“越来越接近查询”的边在图中导航。

HNSW 的核心不只是近邻图，而是“稀疏高层负责远距离跳转，稠密底层负责局部搜索”的分层结构。

## 为什么近邻图可以检索

如果每个向量都连接若干相近向量，那么在当前节点处比较它的邻居，通常能找到一个更靠近查询的节点。不断移动，就能从远处逐步接近目标区域。

只有局部边的普通近邻图可能需要走很多步，也容易陷入局部最优。小世界图会保留少量跨越较远区域的连接，使任意两个区域之间通常只需较少跳数。HNSW 再为这张图增加层级，进一步提高长距离导航效率。

## 分层结构如何形成

每个新节点都会随机获得一个最高层级，层级服从指数衰减分布。可以直观理解为：

- 第 0 层包含所有节点和最完整的局部连接。
- 第 1 层只包含其中一部分节点。
- 越高层节点越少，图越稀疏，边跨越的空间范围通常越大。
- 极少数节点出现在最高层，充当全图导航入口。

某节点出现在至少第 $l$ 层的概率随 $l$ 指数下降，常写成：

$$
P(L \ge l) \propto e^{-l / \lambda}
$$

这种结构类似跳表：高层用于快速越过大段空间，下降到底层后再做细粒度定位。层级由随机过程决定，不需要对向量执行聚类训练。

## 图中保存什么

每个节点保存：

1. 商品向量或可用于计算距离的表示。
2. 业务 ID。
3. 它在每一层的邻居列表。

参数 `M` 控制每个节点保留的连接规模。连接不是简单选择距离最近的 `M` 个节点；成熟实现通常使用启发式邻居选择，在“足够接近”和“方向多样”之间平衡。如果邻居都挤在同一方向，图可能缺少通往其他区域的有效边。

## 构建过程

HNSW 逐个插入节点。插入新向量 $\boldsymbol x$ 时：

1. 随机采样新节点的最高层级。
2. 从全局入口点的最高层开始。
3. 在高于新节点最高层的各层执行贪心搜索，每次移动到更靠近 $\boldsymbol x$ 的邻居，逐层下降。
4. 到达新节点也会出现的层后，使用宽度为 `ef_construction` 的候选搜索寻找一批近邻。
5. 通过邻居选择策略保留至多约 `M` 个连接。
6. 建立双向边；若旧节点邻居超限，则重新裁剪其邻居列表。
7. 逐层重复，直到第 0 层。

因此 HNSW 构建不是“先算出精确 KNN 图”再分层，而是在插入过程中利用当前图搜索近邻并持续维护连接。插入顺序、搜索宽度和随机种子都会影响最终图质量。

## 查询过程

### 1. 高层贪心下降

从最高层入口点开始，检查当前节点的邻居。只要存在距离查询更近的邻居，就移动过去；当前层无法继续改善时，使用该节点作为下一层入口。高层阶段通常只保留一个当前最佳点，目标是快速到达查询所在的大致区域。

### 2. 底层候选扩展

到第 0 层后，使用 best-first 搜索维护两个集合：

- **待探索候选队列**：按“离查询最近”优先弹出。
- **当前最佳结果集合**：保留至多 `ef` 个已发现的较近节点。

每次从候选队列取出最近节点，访问其未见过的邻居并计算距离。若邻居足够好，就加入候选队列和结果集合。当队列中最好的待探索节点也不可能优于当前结果集合中最差的节点时，搜索停止，最后从集合中返回 Top-K。

`ef` 越大，搜索同时保留的路线越多，越不容易被局部最优阻断，但访问节点数和延迟也越高。它至少应不小于 `top_k`。

## 三个核心参数

| 参数 | 作用阶段 | 增大后的效果 | 主要代价 |
| --- | --- | --- | --- |
| `M` | 构建与存储 | 图连通性和召回通常提高 | 邻接表内存、构建和查询访问量增加 |
| `ef_construction` | 构建 | 插入时看到更多候选，边质量通常提高 | 构建更慢、构建期计算量增加 |
| `ef` | 查询 | 探索更多路径，Recall@K 通常提高 | 查询延迟增加 |

`M` 与 `ef_construction` 决定索引本身的质量，修改后通常需要重建；`ef` 是在线查询旋钮，可以在同一索引上调整。较小的 `M` 无法总靠无限增大 `ef` 完全弥补，因为缺失的关键连接根本不在图中。

## 与示例代码的对应关系

[index.py](./index.py) 使用 `hnswlib`：

- `hnswlib.Index(space="cosine", dim=dimension)`：指定距离语义和向量维度。
- `init_index(..., M=16, ef_construction=200)`：分配容量并设置建图参数。
- `add_items(vectors, item_ids)`：逐批插入向量，并直接把业务 ID 作为节点标签。
- `set_ef(80)`：设置查询阶段候选宽度。
- `knn_query(..., k=5)`：执行分层导航和底层候选搜索。
- `save_index` / `load_index`：持久化并重新加载图结构。

运行示例前安装依赖：

```powershell
pip install hnswlib
python .\index.py
```

`hnswlib` 在 `cosine` 空间返回的是距离，通常可理解为 $1 - \text{cosine similarity}$，因此数值越小越近。不同向量库对“分数”与“距离”的符号和范围定义不同，接入时必须确认。

## 更新、删除与内存

HNSW 的优势是无需训练中心或码本，并支持增量插入；但这不代表更新完全免费：

- 新增节点需要在线搜索并修改多个邻接表。
- 删除常使用逻辑标记，长期频繁删改可能留下不可用节点和图碎片。
- 更新向量相当于节点位置改变，旧连接可能不再合理。
- 除向量本身外，每个节点还保存多层邻接表，内存通常明显高于 Flat。
- `max_elements` 需要预留容量，容量规划不当会影响更新流程。

生产环境应测量索引常驻内存、增量写入吞吐、删除后的召回变化和周期性重建成本，而不只是静态查询延迟。

## 常见误区

- **认为图搜索一定返回精确近邻**：搜索路径和候选宽度有限，仍可能错过真实 Top-K。
- **只调 `ef` 不评估建图质量**：低质量连接会给查询召回设置上限。
- **把 `M` 当作严格节点度数**：不同层和实现中的最大连接数可能有额外规则。
- **忽略过滤问题**：先搜后过滤可能导致结果不足；高过滤比例需要扩大候选或使用过滤感知方案。

理解 HNSW 可以抓住两个阶段：高层用少量节点完成全局定位，底层用受 `ef` 限制的候选搜索完成局部探索。
