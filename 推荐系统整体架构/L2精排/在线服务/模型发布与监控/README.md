# 模型发布与监控

模型发布与监控解决的是：如何将一次 L2 改动从“离线看起来更好”推进到“线上可验证、可定位、可恢复的候选级决策”。发布的对象不是单个权重文件，而是一组彼此兼容的制品与运行配置；监控的目标也不只是报警，而是让服务、特征、预测、路由和业务结果能够关联到同一个请求事实与版本组合。

返回[在线服务导航](../README.md)或[在线服务综述](../在线服务综述.md)。

本页约束模型、特征、校准、融合和运行时如何被联合治理。特征字段本身的时间语义见[特征服务](../特征服务/README.md)，单路径性能回归见[推理优化](../推理优化/README.md)，级联和故障路径的选择见[级联与降级](../级联与降级/README.md)。L3 最终施加的列表约束、频控和合规规则必须作为端到端评估的上下文被记录，不能被误归因给 L2。

## 1. 发布对象：可兼容的决策制品包

对 L2 而言，一个可发布版本可以表示为：

$$
R=(M, S, V, N, C, U, I, P)
$$

其中 $M$ 为模型权重与结构，$S$ 为特征 schema，$V$ 为词表/embedding 映射，$N$ 为归一化和缺失规则，$C$ 为校准器，$U$ 为效用融合配置，$I$ 为候选输入接口，$P$ 为运行时与性能配置。只有这些部分共同兼容时，模型输出才有原先定义的意义。

| 制品或配置 | 典型内容 | 为什么必须纳入发布版本 |
| --- | --- | --- |
| 模型制品 | 权重、结构、任务输出、输入 shape | 决定原始预测和运行兼容性 |
| 特征契约 | schema、字段类型、默认值、缺失位、编码位置 | 防止同名字段改变含义或顺序 |
| 映射与统计 | 词表、OOV、分桶、归一化参数 | 保证离散 ID 与连续数值可重现 |
| 校准与融合 | 温度、isotonic、任务权重、效用函数 | 原始分与最终排序分可能并不相同 |
| 候选接口 | L1 通道、分数方向、排名、候选版本 | 防止训练与服务使用不同候选语义 |
| 路由配置 | 级联 K、轻量路径、熔断和回退阈值 | 会改变哪些候选走哪种模型 |
| 运行时配置 | 引擎、精度、编译图、batch 策略、硬件约束 | 影响延迟、资源和数值误差边界 |

制品包应有不可变 ID、兼容性清单、构建来源、审批/验证结果和可获取的历史副本。权重、词表或校准器任一方更新都需要重新校验兼容性；若采用双读或双写迁移，应在清单中显式声明过渡窗口和回收条件。

## 2. 渐进发布链路

```mermaid
flowchart LR
	A[训练与构建制品包] --> B[兼容性和安全校验]
	B --> C[固定请求回放]
	C --> D[压测与故障演练]
	D --> E[Shadow: 真实请求不影响用户]
	E --> F[小流量灰度]
	F --> G[随机实验与分场景放量]
	G --> H[全量与持续观测]
	B --> I[制品注册表与版本清单]
	I --> C
	E --> J[预测、性能和路径差异]
	F --> K[一键回滚稳定制品包]
	G --> K
	H --> K
```

每一阶段回答的问题不同，不能相互替代。

| 阶段 | 要验证的事实 | 不足以证明什么 |
| --- | --- | --- |
| 兼容性校验 | schema、词表、shape、校准器和运行时可共同加载 | 预测质量或真实延迟 |
| 固定回放 | 输入编码、原始输出、校准和候选排序可复现 | 真实流量下的依赖与排队行为 |
| 压测/演练 | P99、资源、回退和异常路径受控 | 用户业务价值 |
| Shadow | 真实请求形状下预测、版本和性能差异可解释 | 新策略一定提升业务指标 |
| 灰度 | 小范围用户的稳定性、护栏与回滚能力 | 统计显著的整体业务结论 |
| 随机实验 | 主指标、长期指标与供给/体验护栏 | 所有场景、所有时间段都同样有效 |

Shadow 应使用同一份候选与特征快照并关联主路径和影子路径版本，比较编码后输入、logit、校准分、融合分、路由与耗时。Shadow 不向用户改变排序，因此只能验证一致性、性能和异常分布，不能替代随机实验。

## 3. 放量门禁与回滚

发布策略应预先声明每个阶段的进入条件、暂停条件、回滚动作和负责人。门禁应同时覆盖正确性、服务稳定性、预测语义和业务护栏；只用单一 CTR 或平均延迟作放量依据很容易掩盖严重回归。

| 类别 | 放量前检查 | 暂停或回滚信号 |
| --- | --- | --- |
| 契约 | 制品清单完整，接口和 schema 兼容 | 版本校验失败、未知字段、词表错配 |
| 服务 | P99、错误率、队列、资源和回退率符合预算 | 超时/错误突增、资源饱和、回退异常 |
| 特征 | 缺失、OOV、新鲜度和来源分布稳定 | 关键字段缺失、陈旧读或分布断层 |
| 预测 | logit/概率分位数、NaN、ECE、路径分布可解释 | 数值异常、校准恶化、Top-K 大幅变化 |
| 业务 | 主目标、负反馈、供给、合规和体验护栏 | 护栏突破，或效果在关键分群恶化 |

回滚应切回一个已验证的**完整制品包**，而非只撤销权重。需要明确回滚范围：模型、词表、schema、校准器、路由与运行时是否一并切换；同时保留新旧版本的请求占比和生效时间，避免事件发生后无法判断哪些请求受影响。

对于无法立即切换的变更，例如 schema 迁移或基础设施升级，应提供兼容窗口、双读/双写策略、开关优先级和紧急稳定路径。回滚演练应验证切换时间、缓存/编译预热、输出契约及 L3 兼容性，而不仅是控制台上的配置修改成功。

## 4. 请求关联与可回放性

一条 L2 结果应能关联到输入事实和执行事实，而非记录所有原始用户数据。建议为请求建立可检索的版本与状态摘要：

| 关联维度 | 最小记录内容 | 用途 |
| --- | --- | --- |
| 请求与实验 | request ID、场景、实验桶、时间和流量入口 | 分析影响范围和实验归因 |
| 候选 | 候选 ID、L1 通道、原始分、排名、候选接口版本 | 重建 L2 的竞争集合 |
| 特征 | schema/词表版本、来源、缺失/过期状态、快照引用 | 定位训练服务不一致与依赖问题 |
| 执行 | 模型、校准器、融合、运行时、路由和硬件版本 | 分离模型、配置和基础设施影响 |
| 输出 | 任务 logit、校准分、融合分、路径和状态码 | 诊断预测与排序语义 |
| 后续结果 | L3 最终位置/曝光状态、反馈、归因窗口 | 区分 L2 输出与最终业务结果 |

日志需满足最小化、权限控制、脱敏和留存要求。对敏感特征优先保留版本、状态和受控快照引用；回放时在受权限保护的环境中读取原始事实，避免把用户数据复制到普通诊断日志。

## 5. 分层监控与告警

监控应按因果链分层：服务是否能完成，特征是否仍代表预期事实，预测是否保持数值语义，路由是否按设计运行，以及最终用户结果是否改变。各层按模型、特征、校准器、路由、场景、实验桶和关键人群切片，才能从“指标异常”走到可行动的定位。

| 层次 | 核心指标 | 常见诊断方向 |
| --- | --- | --- |
| 服务 | QPS、P50/P95/P99、错误、队列、资源、成本 | 流量峰值、运行时、依赖或容量问题 |
| 特征 | 缺失、OOV、新鲜度、来源、数值分位数、漂移 | schema 迁移、上游延迟、词表和统计异常 |
| 推理与路由 | 加载失败、NaN、路径占比、回退率、K 值 | 模型/量化异常、熔断、预算和设备健康 |
| 预测 | logit/概率/融合分分位数、ECE、任务关系、Top-K 变化 | 校准失效、输入漂移、数值或配置回归 |
| 业务 | L3 后曝光、CTR/CVR、时长、负反馈、供给、留存 | 策略影响、流量构成变化或指标归因问题 |

告警优先围绕可行动且有持续性的异常设置：例如关键特征缺失、新版本 NaN、回退率突升、P99 破预算、预测分布断层或业务护栏突破。将所有短暂波动直接报警会制造噪声，反而掩盖真正需要回滚的变化。阈值可采用静态 SLO、历史季节性基线和版本对照，但应写清适用场景与负责人。

## 6. 事件响应与定位顺序

当业务指标或预测分布异常时，先确认请求是否确实进入了目标版本，再沿输入到输出的链路缩小范围：

1. 确认版本占比、实验桶、场景和生效时间，排除流量切换或日志延迟。
2. 检查服务 P99、错误、队列和回退，判断是否为容量或依赖问题。
3. 检查特征 schema、缺失、OOV、新鲜度与编码后分布，定位输入变化。
4. 对同一请求快照回放新旧制品，比较 logit、校准、融合分和路由路径。
5. 将 L2 输出与 L3 最终曝光和业务反馈关联，避免把列表约束或流量差异误判为模型问题。
6. 若护栏或语义契约被破坏，优先回滚到稳定制品包，再进行离线复盘。

这套顺序强调先恢复系统的可控状态，再追求完整根因；运行中的实验不应成为排障时唯一的证据来源。

## 7. 实施清单

1. 将模型、schema、词表、归一化、校准、融合、路由和运行时构建为不可变、可查询的制品包。
2. 为每个包自动校验兼容性，并在固定回放集上验证编码、预测、校准和排序。
3. 依次完成压测、故障演练、Shadow、灰度和随机实验；为每阶段写明门禁与负责方。
4. 设计完整包的快速回滚、兼容迁移和预热流程，并定期进行演练。
5. 用 request ID 将候选、特征状态、执行版本、L2 输出、L3 最终结果和反馈关联起来。
6. 分层监控服务、特征、预测、路由和业务；按版本、场景和实验桶建立可行动的告警与排障面板。

## 常见误解

- **只发布模型权重即可回滚**：词表、schema、归一化、校准器、融合参数、路由和运行时同样属于发布版本。
- **Shadow 指标正常就可以全量**：Shadow 只能确认预测与性能，业务收益和护栏仍需随机实验验证。
- **服务稳定就说明效果稳定**：数据漂移、校准偏移、路由变化和 L3 后曝光差异需要独立监控。
- **监控图表越多越安全**：关键是建立能关联版本、请求事实和后续结果的可行动信号。
- **出问题先找模型原因**：应先确认版本和流量，再沿服务、特征、预测、L3 结果逐层定位。
