# 多场景与迁移

多场景与迁移解决的是：首页、频道、搜索、详情页、地域或业务线之间，哪些规律应共享，哪些差异应保留。场景差异可能来自用户意图、候选来源、展示位置、特征可用性、标签基准率和业务目标；只有这些差异稳定、可观测且有足够样本时，专门的共享/适配结构才有意义。

场景结构不替代 L3 的页面规则、频控和合规约束，也不应掩盖跨场景的标签口径不一致。模型输入与特征服务要求见[数据与特征](../../数据与特征/README.md)，跨任务共享问题见[多任务学习](../多任务学习/README.md)。

## 共享、独立与适配的选择

| 策略 | 优势 | 局限 | 适用条件 |
| --- | --- | --- | --- |
| 全局单模型 | 数据利用率高、维护简单 | 小场景或强差异场景可能被平均化 | 场景差异弱，标签和特征一致 |
| 每场景独立模型 | 可充分适配本地规律 | 长尾场景样本不足、发布成本高 | 大场景数据充足且目标明显不同 |
| STAR 类共享 + 场景参数 | 平衡共享与差异，减少模型数量 | 场景定义、参数路由和冷启动更复杂 | 共享主体明显、差异稳定可量化 |
| Adapter/门控等场景自适应 | 适配层轻量，可逐步扩展 | 容易把噪声分桶学成“场景” | 需要快速试验多种差异假设 |

选择前应以全局模型、按场景独立模型和简单场景特征模型作为对照。只有复杂适配结构在主要场景、长尾场景和跨场景用户上都显示可复现净收益，才值得长期维护。

## 场景定义与迁移边界

场景 ID 应对应稳定、可回放的决策语境，例如明确入口、页面类型、地域或业务域。一个场景内混入多种候选策略、标签口径或页面规则时，模型会将工程差异误学为用户偏好。

| 需先检查的差异 | 可能处理方式 | 不应直接归因给模型 |
| --- | --- | --- |
| 候选来源或 L1 通道不同 | 保留通道特征、按场景评测 | “场景兴趣不同” |
| 标签基准率、窗口不同 | 统一标签或独立任务头 | “共享模型不够强” |
| 特征覆盖或时延不同 | 补齐 schema、定义默认值 | “需要更多场景参数” |
| 页面布局与位置不同 | 记录展示口径、交由 L3 规则 | “用户偏好发生迁移” |

新增场景可采用共享模型冷启动、场景 embedding/adapter 初始化、少量样本校准和逐步灰度。不要在没有样本的场景上训练独立大模型，也不要让新场景的未知 ID 静默映射为任意既有场景。

## 评测与发布检查

- 按场景、跨场景用户、新增场景、冷热门物品和候选通道报告排序、概率和业务指标；总体平均值不足以支持结论。
- 检查各场景样本量、标签成熟度、特征缺失/OOV、候选数与位置分布，定位数据而非结构差异。
- 对共享参数、场景参数、adapter/门控做消融，并监控小场景是否被大场景吞没。
- 将场景路由、参数版本、默认场景与回退模型一起发布；路由异常时可降级到稳定共享模型。
- 线上实验设置每场景护栏和全局资源预算，关注 P99、错误率、跨场景串扰与长期价值。

## 常见误解

- **每个入口都应该独立训练模型**：共享程度由数据规模、特征重合和目标一致性决定。
- **场景 embedding 足以解决所有域差异**：候选、标签、特征和页面机制也可能发生变化。
- **全局提升说明所有场景都受益**：必须分别评估主要、长尾和跨场景人群。
